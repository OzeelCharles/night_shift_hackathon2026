## Reproduction

Insertion directe par `sqlite3` (sans la validation Python) dans la base créée par l'application. Toutes ces lignes
sont **acceptées** :

- `grades` : `value = -1`, `value = 25` pour `out_of = 20`, `out_of = 0` ou `-20`, `coefficient = 0` ou `-2` ;
- `events` et `sessions` : `end = start`, `end < start`, `start = 'demain'`, `start = ''` ;
- `preferences` : `session_minutes` 9 et 241, `break_minutes` -1 et 61, `daily_max_minutes` 29 et 961,
  `horizon_weeks` 0 et 27 ;
- `users` : `ELEVE@TEST.FR` et `Eleve@Test.fr` alors que `eleve@test.fr` existe (pas de `COLLATE NOCASE`) ;
  `is_active = 2`.

Impact : seule la validation Python protège la cohérence ; un bogue, un script ou une future route peut écrire des
données incohérentes (notes impossibles, séances de durée négative, doublons d'adresse).

Résultat attendu : `CHECK` et `COLLATE NOCASE` du cahier, posés par une migration qui recrée les tables dans une
transaction, sous un nouveau `user_version`. Attention : le service accepte aujourd'hui `daily_max_minutes` de 20 à
29 alors que le cahier fixe 30 au minimum (il faudra aligner le service pour éviter des 500).

Conforme (testé) : `PRAGMA foreign_keys = ON` sur les connexions de l'application, y compris dans un fil en
arrière-plan.

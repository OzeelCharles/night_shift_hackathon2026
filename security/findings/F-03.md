# F-03 — Aucune limite de tentatives sur la connexion et l'inscription

- **Gravité** : Moyenne
- **Exigence** : SEC-03
- **Trouvée par** : attaquant, manche 1, le 2026-11-27
- **Route / fichier** : `POST /connexion`, `POST /inscription` — `backend/controllers/auth.py:14` et `:31`, `backend/services/auth_service.py:36`
- **Statut** : ferme

## Reproduction

1. Compte `cible@test.fr` existant. Depuis une même IP (`REMOTE_ADDR` simulée), 5 connexions avec un mauvais mot de passe.
2. 6e tentative avec un mauvais mot de passe, puis 7e avec le bon.
3. Variantes : 6 tentatives sur le même compte depuis 6 IP différentes (limite par compte) ; un mot de passe essayé
   sur 6 comptes différents depuis la même IP (pulvérisation, limite par IP) ; boucle de 60 mauvais essais puis le bon
   (attaque « 1 000 tentatives » du cahier, bornée à 60 pour rester rapide).
4. Inscription : 6 comptes créés depuis la même IP en quelques millisecondes.

Charge utilisée : `POST /connexion` `email=cible@test.fr&password=Mauvais-Mot-De-Passe-0`, `environ_base={"REMOTE_ADDR": "198.51.100.7"}`.

Résultat observé : 6e échec = 200 (formulaire réaffiché) ; 61e essai avec le bon mot de passe = 302 (connecté) ;
6e inscription = 302, 6 comptes créés. Aucun blocage, aucun délai.

Résultat attendu : 6e échec (par compte et par IP, en 15 min) = 429 avec message neutre, le bon mot de passe
restant refusé pendant le blocage ; 6e inscription depuis une IP dans l'heure = 429, pas de 6e compte.

Note pour la correction : les tests tournent avec `TESTING=True` ; la limite doit rester active dans ce mode
et son état doit être propre à chaque application (pas d'état global de module partagé entre les tests,
sinon les autres tests qui inscrivent des comptes depuis 127.0.0.1 seraient bloqués).

## Correction (rempli par le défenseur)

- Fichiers modifiés : `backend/services/auth_service.py` (`login`, `register`), `backend/dao/auth_attempts.py` (nouveau), `backend/dao/db.py` (migration 2 : table `auth_attempts`), `backend/controllers/auth.py`, `backend/config.py`, `backend/tests/test_migration_sessions.py` (nouveau)
- Principe : avant toute vérification, le service compte les échecs récents par compte (e-mail normalisé) et par IP sur 15 min : à 5, toute tentative (même avec le bon mot de passe) reçoit 429 et un message neutre ; inscription : 5 par IP et par heure (adresse déjà prise comprise), puis 429. L'état est dans la base de l'application (propre à chaque instance, partagé entre workers WSGI, clés hachées SHA-256), actif en TESTING ; seuils dans la config (`LOGIN_MAX_FAILURES`, `LOGIN_WINDOW_SECONDS`, `REGISTER_MAX_PER_IP`, `REGISTER_WINDOW_SECONDS`). Le compteur du compte est remis à zéro après une connexion réussie. IP = `request.remote_addr` : derrière un proxy, `ProxyFix` (DEP-01) sera nécessaire.

# F-014 — Un administrateur peut se rétrograder ou se désactiver lui-même

- **Gravité** : Basse
- **Exigence** : SEC-02
- **Trouvée par** : attaquant, manche 1, le 2026-11-27
- **Route / fichier** : `POST /admin/utilisateurs/<user_id>` — `backend/services/admin_service.py:41`
- **Statut** : ferme

## Reproduction

1. L'admin initial crée un second admin (`POST /admin/utilisateurs/nouveau`, `role=admin`).
2. L'admin initial envoie `POST /admin/utilisateurs/<son_id>` avec `role=user` (ou sans `is_active`).

Résultat observé : son rôle passe à `user` (le contrôle `losing_admin` ne protège que le **dernier** admin actif).

Résultat attendu (cahier SEC-02) : « Un admin ne peut ni se supprimer, ni se rétrograder, ni désactiver le dernier
admin actif » : la modification de son propre rôle ou de son propre statut est refusée.

Conforme (testé) : un admin ne peut pas se supprimer ; le dernier admin actif ne peut être ni rétrogradé ni désactivé ;
un utilisateur simple reçoit 403 sur toutes les routes `/admin` (GET et POST, données inchangées) ; un visiteur est
renvoyé vers `/connexion`.

Impact : pas d'élévation de privilège ; perte de contrôle accidentelle ou par une session admin volée. Gravité Basse.

## Test qui reproduit

`backend/tests/security/test_sec_02_controle_acces.py::AccesAdministrationTests::test_admin_ne_peut_pas_se_retrograder_meme_avec_un_autre_admin` (échoue avant la correction)

## Correction (rempli par le défenseur)

- Fichiers modifiés : `backend/services/admin_service.py` (`update_user`), `backend/controllers/admin.py`
- Principe : `update_user` reçoit l'identifiant de l'admin connecté et refuse toute modification qui lui ferait perdre son rôle ou son statut actif (même s'il existe d'autres admins) ; la règle du dernier admin actif reste en place pour les autres comptes.
